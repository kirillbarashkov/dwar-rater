### A1. ✅ ЗАКРЫТО (2026-10-20) — Записи `audit_log` терялись в 11 админских операциях

**Severity: High.** Где: `backend/features/admin/routes.py` — строки 138, 154, 173,
218, 236, 374, 430, 532, 625, 650, 705.

**Что не так.** Хелпер `_audit()` (`features/admin/routes.py:30-41`) только делает
`db.session.add(entry)` — сама запись появляется в БД лишь при следующем `commit()`.
В 11 местах `_audit()` вызывается **после** `db.session.commit()`, и следующего
коммита уже нет: запрос завершается, сессия откатывается, запись пропадает.

**Почему это важно.** Журнал аудита — то, по которому видно, кто и что менял.
Он молча неполон ровно для тех операций, которые меняют доступы и данные:
деактивация пользователя, отзыв сессий, выдача/снятие прав, удаление бэкапа,
восстановление БД из бэкапа. Восстановить из журнала, кто деактивировал
сотрудника или кто отозвал сессии, невозможно.

**Как доказано.** Проба-тест (временный файл, удалён после прогона) создала
пользователя, вызвала `PUT /api/admin/users/<id>` и `DELETE /api/admin/users/<id>`
с правами админа и посчитала строки `audit_log` до и после:

```
PUT status: 200 {'id': 2, 'is_active': True, ...}
audit rows user_update: before=0 after=0        ← запись потеряна
DELETE status: 200 {'status': 'deactivated', ...}
audit rows user_deactivate: before=0 after=0    ← запись потеряна
```

Ответ 200, действие применено, записи нет.

**Связь с уже закрытым долгом.** В таблице «Закрытые долги» есть строка
«`_audit()` без последующего `commit()` — запись теряется | v2.5.0: `commit()`
после каждого `_audit`». Долг закрыли **только в `features/clan_info/routes.py`** —
там `commit()` после `_audit()` действительно есть (проверено: 18 из 19 вызовов
закрыты коммитом). В `features/admin/routes.py` его никто не делал. То есть
закрытие долга TD-«_audit без commit» было неполным, и **регрессия живёт в
проде прямо сейчас**.

**Рекомендация.** Два пути, на выбор владельца:

1. Перенести `_audit()` **до** `db.session.commit()` во всех 11 местах — запись
   попадёт в БД тем же коммитом, что и сама операция. Минимальная правка и правильная
   атомарность: операция и её след в журнале фиксируются вместе.
2. Сделать `_audit()` самодостаточной: внутри хелпера выполнить `db.session.commit()`
   после `add`. Проще, но теряет атомарность (операция закоммичена, след — нет).

| Места | Было | Стало |
|---|---|---|
| 8 операций | `_audit()` **после** `commit()` | `_audit()` перед коммитом |

- `_audit()` обязан стоять **до** `commit()`; проверять надо не «вызвали ли

### A2. ✅ ЗАКРЫТО (2026-10-21) — Уровень права `read` проходил гейт `admin` (SSE, force_refresh)

**Severity: High.** Где: `backend/features/clan_info/routes.py:4586`, `:4715`, `:5221`.

**Что не так.** Три SSE-эндпоинта (поток автосбора казны, поток автосбора состава,
поток импорта событий уровня) **не имеют** декоратора `@require_permission` —
вместо этого авторизация проверяется вручную:

```python
if not current_user or get_user_permission(current_user, "treasury", "admin") == "none":
    # отказ
```

Проверяется лишь «не `none`». Но `require_permission`
(`backend/shared/rbac/__init__.py:220`) для действия `admin` явно **запрещает**
уровень `read`:

```python
if level == 'read' and action in ('write', 'delete', 'admin', 'approve'):
    return jsonify({'error': 'Недостаточно прав'}), 403
```

То есть ручная проверка **слабее** той, что декларирует остальной проект.

**Почему это важно.** В матрице прав уровень `read` — это «видно, но нельзя
менять». Администратор может выдать пользователю `treasury:admin = read`
(«смотрю казну, но не правлю»), рассчитывая, что автосбор и правка недоступны.
На SSE-эндпоинтах этот пользователь **проходит гейт** и получает поток данных
казны, к которому при определённых условиях прилагается и запись в базу
(импорт событий уровня — это запись в `clan_level_change_event`).

**Как доказано.** Проба-тест выдала пользователю индивидуальное право
`treasury:admin = 'read'`, выдала сессию и дёрнула SSE-эндпоинт:

```
SSE status: 200
SSE body: {"type": "error", "reason": "no_valid_cookies", ...}
```

Ответ дошёл до проверки cookies — значит, **гейт прав был пройден**. При
уровне `none` тот же запрос вернул бы `reason: "forbidden"`. Уровень `read`
получил доступ, который `require_permission` ему не даёт.

**Вторая половина того же дефекта.** Ручная проверка **не проверяет
`user.is_active`** — а `require_permission` проверяет
(`shared/rbac/__init__.py:212-213`). Деактивированный пользователь или
пользователь, у которого админ отозвал сессии, продолжает стримить данные казны
до истечения TTL токена (24 ч для обычного пользователя).

**Рекомендация.** Не чинить проверку копией логики, а **свести к одному
источнику истины**: вынести проверку в переиспользуемый декоратор, который
принимает токен из query-параметра (нужно для `EventSource`, который не умеет
заголовки):

```python
def require_permission_from_token(feature, action):
    # проверяет: токен валиден И не истёк И user.is_active И уровень достаточен
```

и повесить его на все три SSE-эндпоинта. Тогда «ручная проверка» и
`require_permission` не смогут разойтись снова.

**Решение (2026-10-21).** Вместо отдельного декоратора — хелпер
`has_permission(user, feature, action)` + приватная `_level_allows(level, action)`
в `shared/rbac/__init__.py`. Причина: декоратор не годится для SSE (там нужен
ответ событием `error/forbidden` со статусом 200, а не 403), а правило «read не
даёт изменяющих действий» должно жить **в одном месте**. `require_permission`
теперь тоже ходит через `_level_allows`, поэтому ветки физически не могут
разойтись.

**Класс дефекта оказался шире трёх SSE.** Тот же `== 'none'` стоял ещё в трёх
местах на гейте `write`:

| Файл | Действие | Было |
|---|---|---|
| `features/clan_info/routes.py:4589` | `treasury:admin` (SSE) | `read` проходил |
| `features/clan_info/routes.py:4718` | `clan_info:admin` (SSE) | `read` проходил |
| `features/clan_info/routes.py:5224` | `clan_info:admin` (SSE) | `read` проходил |
| `features/analyze/routes.py:24` | `analyze:write` (force_refresh) | `read` проходил |
| `features/tracks/routes.py:110` | `analyze:write` (force_refresh) | `read` проходил |
| `features/tracks/routes.py:173` | `analyze:write` (force_refresh) | `read` проходил |

То есть пользователь с `read` мог не только запускать импорт казны/состава/
уровней, но и заставлять сервер перезапрашивать персонажа с dwar.ru
(единственное место, где `read` давал реальный расход ресурсов).

`features/clans/routes.py:39` (`clans:write == 'full'`) не тронут — там проверка
строже правила, дефекта нет.

**Тест:** `backend/tests/test_permission_levels.py` — 7 тестов: три SSE,
два force_refresh, контроль «full по-прежнему проходит» и проверка самого
правила `_level_allows`. Контрольный тест важен: без него фикс мог бы закрыть
доступ всем.

**Грабли теста:** `SessionToken` не принимает `token=` — хранится
`token_hash=SessionToken.hash_token(token)` плюс обязательный `expires_at`.

### A3. ✅ ЗАКРЫТО (2026-10-20) — Слепок сохранялся не в JSON

**Severity: High.** Где: `backend/features/closed_profiles/routes.py:230`.

**Что не так.** При сохранении слепка закрытого профиля данные кладутся в колонку
`CharacterSnapshot.snapshot_data` (`db.Text`) через `str(snapshot_data)` —
это Python-repr словаря, а не JSON:

```python

```

Все остальные писатели используют `json.dumps(..., ensure_ascii=False)`
(`shared/services/cache_service.py:37` и `:54`), и все читатели — `json.loads`:

- `features/snapshots/routes.py:62` — `json.loads(snapshot.snapshot_data)`
- `features/export/routes.py:64` — `json.loads(snapshot.snapshot_data)`
- `features/tracks/routes.py:55` — `json.loads(snapshot.snapshot_data)`

`json.loads` на Python-repr падает с `JSONDecodeError`. Ломаются три сценария:
просмотр слепка, экспорт персонажа в HTML/PDF, трек улучшений. Ошибка приходит
как 500 на чтении.

**Как доказано.** Проба-тест (round-trip `str(dict)` → `json.loads`):

```
json.loads FAILED: JSONDecodeError: Expecting property name enclosed in double quotes: line 1 column 2 (char 1)
```

Контрольный вариант с `json.dumps` проходит.

**Почему это не поймали.** На фичу `closed_profiles` **нет ни одного теста**
(в `backend/tests/` слово `closed_profiles` встречается только в `conftest.py`),
и на фичу `export` — тоже ноль тестов (`export_to_pdf`/`export_to_html`/
`export_to_markdown` не упоминаются ни в одном тестовом файле). Это ровно тот
класс дефекта, который тестовая матрица не покрывает.

**Рекомендация.** Заменить `str(...)` на `json.dumps(snapshot_data, ensure_ascii=False)`
— одна строка. Плюс: **тест на round-trip** для `closed_profiles` (записал →
прочитал → сравнил) и тесты на `export_*` — обе фичи сейчас без покрытия.

**Решение (2026-10-20).** `str(snapshot_data)` → `json.dumps(snapshot_data,
ensure_ascii=False)` (`features/closed_profiles/routes.py:232`), плюс импорт `json`.
Добавлен `backend/tests/test_closed_profiles.py` — два теста:

1. `test_saved_snapshot_is_valid_json` — пишет слепок через API и разбирает
   значение из БД через `json.loads`;
2. `test_snapshot_is_readable_by_the_api` — проверяет, что читательский
   `GET /api/snapshots/<id>` отвечает 200 (до правки он падал с
   `JSONDecodeError` прямо в `snapshots/routes.py:62`).

**Проверка:** тест падал с `json.decoder.JSONDecodeError` **на настоящем
эндпоинте** (не на искусственном round-trip) — то есть дефект воспроизведён
в пользовательском сценарии. После правки — 2 passed, и на чистой, и на
грязной БД, и в обоих порядках запуска с `test_snapshots.py`.

**Две грабли, на которые наступил при написании теста** (общий TRUNCATE в
conftest — молчаливый no-op, см. A61, поэтому тест обязан убирать за собой):

- **Порядок удаления.** `closed_profiles.snapshot_id` — FK на
  `character_snapshot`, поэтому профиль обрываем первым (`snapshot_id → NULL`),
  иначе `ForeignKeyViolation`.
- **Тест обязан чистить за собой.** Без этого `test_snapshots_empty_list`

**Осталось (не в объёме A3):** на фичу `export` тестов по-прежнему ноль
(`export_to_pdf`/`export_to_html`/`export_to_markdown` не покрыты) — это

#### A6. ✅ ЗАКРЫТО (2026-10-23) — `create_all()` больше не запасной путь миграций в проде

**Severity: High.** Где: `backend/app.py:226-227`.

Если Alembic-апгрейд падает, код логирует предупреждение и вызывает
`db.create_all()` — создаёт схему по моделям, **без данных и без истории
миграций**. `create_all()` не добавляет столбцы в существующие таблицы: модель
наехала на старую таблицу → `UndefinedColumn` во время работы, а не на старте.
Плюс к этому `alembic_version` чистится вручную (`:183`) — «более одного head»
исправляется удалением строк, что маскирует расхождение схемы и миграций.

**Рекомендация.** В проде падение миграции — фатальная ошибка старта, а не
запасной путь. `create_all()` оставить только для SQLite/локальной разработки.
`alembic_version` не чистить, а падать.

**Решение (2026-10-23).** Решение вынесено в
`shared/services/migration_guard.py::handle_migration_failure()`, `app.py`
передаёт туда `strict=Config.STRICT_MIGRATIONS`. Оба `except`-блока (docker-ветка
и fallback-ветка) сведены к одному вызову — раньше код был продублирован, и
правки приходилось делать дважды.

Поведение управляется env-переменной `STRICT_MIGRATIONS`:

| Значение | Поведение |
|---|---|
| `true` (прод, задано в `docker-compose.prod.yml`) | `RuntimeError`, контейнер не стартует |
| `false` (дефолт; dev, тесты, SQLite) | warning + `create_all()`, как раньше |

Флаг, а не «определить прод по драйверу»: поведение обратимо без правки кода —
достаточно снять переменную. По умолчанию выключено, чтобы локальная разработка
на SQLite не падала на первом расхождении, где миграции вообще не применяются.

**Проверка:** `backend/tests/test_strict_migrations.py` — 5 тестов; ключевой
утверждает, что в строгом режиме `create_all()` **не вызывается вовсе**
(передаётся счётчик-заглушка), и что причина исключения сохраняется в `__cause__`.
Плюс тест, что `docker-compose.prod.yml` действительно включает флаг — иначе
фикс был бы no-op.

**Побочная правка:** `data_logger` в `app.py` импортируется **внутри**
`create_app`, поэтому хелпер не может обращаться к нему как к глобальному —
логгер передаётся параметром.

**Почему после A38.** Включать фатальность раньше гарантии готовности Postgres
нельзя: на медленном старте БД это дало бы crash-loop. A38 (healthcheck +
`service_healthy`) вышел отдельным релизом до этой правки.

#### A63. [доказано] Смена пароля не проверяет текущий пароль

**Severity: High.** Где: `backend/features/auth/routes.py`, `change_password`.

Эндпоинт `POST /api/auth/change-password` требует только валидный токен сессии и
`new_password`. Поле `current_password` в теле запроса **игнорируется** — его нет
в коде вообще. То есть пароль меняется без знания старого.

**Как доказано.** Тест `tests/test_auth_audit.py` (первая версия) отправил
`current_password: 'wrong'` с валидным токеном и ожидал 4xx — получил **200**, а
пароль был сменён.

**Последствие.** Любой, кто получил токен сессии (украденный браузер, забытый
открытый ноутбук, XSS), не просто действует от имени пользователя, но и
**забирает аккаунт**: меняет пароль и выбрасывает владельца. Для админских и
superuser-сессий это означает потерю контроля над системой. Обычная практика
(и ожидание пользователя) — подтверждение старым паролем именно для этой
операции.

**Почему не исправлено сразу.** Фронтенд (`frontend/src/api/auth.ts:57`)
присылает только `new_password`:

```ts
await apiClient.post('/api/auth/change-password', { new_password: newPassword });
```

Если просто потребовать `current_password` на бэкенде, форма смены пароля
сломается у всех пользователей. Нужен согласованный срез: поле в форме + запрос
+ проверка `bcrypt.checkpw(current_password, user.password_hash)` и запись
`password_change_failed` в аудит при неверном пароле.

**Рекомендация.** Делать одним изменением бэкенд + фронтенд. Для админов с
включённой 2FA дополнительно требовать код TOTP при смене пароля — иначе
украденный токен обходит второй фактор ровно в самой чувствительной операции.

**Severity: Medium.** Где: `shared/services/clan_parser.py:84`

**Решение (2026-10-24). — Находка описывала не то, что есть на самом деле.**
Проверка вызовов показала: функций разбора состава **три**, и две из них мёртвые.

|---|---|---|---|
| `parse_clan_members` | `clan_parser.py` | **0** | мёртвая и **падающая** |

| `parse_clan_members_from_management` | `clan_parser.py` | `clan_info/routes.py:4838` | живая |

Поэтому «сводить к одной функции с параметром формата входа» было нечего:
дублировались не две рабочие реализации, а живая и две мёртвые.

```python
r"(Глава Ордена|Зам\. Главы.|Совесть.|...|9-ть жЫзней.).|УлитЫчка.).|РудольФ.|Сосиска.)"
#                    ^ вместо '|' — '.', плюс лишние закрывающие скобки
```

`Герой|Властелин боя|Вершитель…`. То есть паттерн требовал literal-строку со
всеми рангами подряд и не мог совпасть ни с одной строкой состава.

**Что сделано:** обе мёртвые копии удалены (`parse_clan_members` — 69 строк;
`shared/services/clan_import.py` — целиком, 61 строка). Живая функция не
тронута. Проверено, что на неё нет ссылок ни в одном `.py`/`.sh`/`.yml` репозитория.

#### A16. ✅ ЗАКРЫТО (2026-10-24) — Парсер глушил исключения при оценке границ казны

**Severity: Medium.** Где: `backend/shared/services/clan_parser.py:500-501` и

```python
except Exception:
    pass
```

Дважды. Если страница казны не отдалась (сеть, смена вёрстки), расчёт границ
молча возвращает пустые `sample_dates` — автосбор стартует с неверных границ

результата.

**Решение (2026-10-24). Найдено четыре молчаливых `except`, а не два.**

Аудит указывал две точки (`pass` при сборе `sample_dates`). При правке

|---|---|---|
| `find_start_boundary` | `except Exception: break` | лог + запись причины |
| `find_end_boundary` | `except Exception: break` | лог + запись причины |
| сбор `newest_page_sample` | `except Exception: pass` | лог + запись причины |
| сбор `oldest_page_sample` | `except Exception: pass` | лог + запись причины |

Сбой в бинарном поиске опаснее `pass`: он молча возвращал неверную границу, и
сбор шёл по чужому диапазону — либо терял старые операции, либо тянул лишние
страницы.

**Что теперь возвращается.** В результат добавлены `boundaries_complete: bool` и
`boundary_errors: list[str]`. Ключи есть во всех точках выхода
`estimate_pages_in_range`, включая ранние возвраты, — иначе вызывающая сторона
получала бы `KeyError` вместо ответа.

**Дошло до интерфейса.** `clan_info` прокидывает оба поля в JSON ответа
`.../treasury/...estimate`, так что клиент видит «границы не определены», а не
молча собирает неполный диапазон.

**Тест:** `backend/tests/test_boundary_errors.py` — 3 теста: сбой сети на
страницах-границах даёт `boundaries_complete=False`, непустой `boundary_errors`

(нет данных) **не** считается сбоем границ — запросы ведь не падали.

**Своя ошибка, пойманная до коммита.** Первый автоматический патч вставил ключи
в ранний возврат `estimate_pages_in_range`, который выполняется **до** объявления
`boundary_errors`, — это был бы `NameError` на живом пути. Поймано проверкой
«в какой функции оказался ключ»; объявление флага перенесено выше первого
`return`.

#### A17. ✅ ЗАКРЫТО (2026-10-24) — Пустой `except:` в модели клана

**Причина уточнена — аудит был неправ в диагнозе.** Утверждение «запрос невалиден,
`pg_stat_file` нельзя класть в `FROM` без `LATERAL`» **опровергнуто измерением**:
запрос выполняется и возвращает строки (`Tables | 35`).

`COUNT(*) FROM (SELECT 1 FROM pg_stat_file('/backups') LIMIT 0) t` — `LIMIT 0`
гарантирует **ноль строк всегда**. Проверено на живом dev-volume: в каталоге лежало
**2046** дампов, а цель печатала `Backups | 0`. Плюс `pg_stat_file` возвращает
атрибуты одного файла и вообще не перечисляет каталог.

| Что | Было | Стало |
|---|---|---|
| Метрика бэкапов | `LIMIT 0` → всегда 0 | `COUNT(*) FROM pg_ls_dir('/backups') … WHERE name LIKE '%.sql.gz'` — реальное число |
| Метрики | 2 | 3: `Tables`, `Users`, `Backups (sql.gz)` |
| Учётные данные | жёстко `-U dwar -d dwar_rater` | `$(PG_USER)` / `$(PG_DB)` из `.env` с fallback'ом |
| Контейнер | `docker exec dwar_rater_postgres` | `docker compose exec -T postgres` (по сервису, не по имени) |
| Ошибки | `2>/dev/null || echo "DB not accessible"` | stderr виден; сообщение больше не перекрывает настоящую причину |

Проверено вручную (на этой машине нет `make`): подставил переменные так же, как это
делает make, и выполнил рецепт — `Tables 35, Users 1, Backups (sql.gz) 2047`.

#### A61. [доказано] Полный прогон на хосте терял 11 тестов — исчерпание пула соединений

**Severity: Medium. ✅ ЗАКРЫТО (2026-10-20).** Где: `backend/tests/conftest.py:103`
(фикстура `app`), `backend/test_app.py:30` (`db.init_app(app)`),
`backend/shared/config.py` (нет `SQLALCHEMY_ENGINE_OPTIONS`).

Это находка **после** основного аудита — всплыла, когда перед коммитом
техдолга прогонялся полный набор тестов на хосте.

**Что не так было.** Фикстура `app` — **function scope** (по умолчанию, без
`scope='session'`). Каждое создание вызывает `create_test_app()` →
`db.init_app(app)` → **новый SQLAlchemy-движок со своим пулом соединений на
каждый тест**. `engine.dispose()` не вызывался нигде. Пул копился, пока
суммарные соединения не упирались в `max_connections=100` — и тогда
`pool.connect()` начинал падать.

**Как было доказано.** Наблюдение во время прогона (счётчик из `pg_stat_activity`):

```
t+45s:  соединений к dwar_rater_test = 34
t+90s:  73
t+135s: 79
t+225s: 94
t+270s: 91, всего по всем БД = 105   (max_connections = 100)
```

Итог прогона на хосте: **435 passed, 11 errors**, все 11 — падение в setup на
`engine.raw_connection()` → `pool.connect()`. Тот же код в контейнере давал
**446 passed**.

**Что оказалось важным при выборе решения.** Побочно выяснилось, что
`_truncate_all()` в conftest — **молчаливый no-op**: в списке TRUNCATE есть
таблица `equipment_item`, которой в тестовой БД нет, поэтому весь TRUNCATE
падает и исключение глотается. То есть БД между тестами **не чистится
вообще**, и часть тестов чистит свои кланы явно (см. комментарий в
`tests/test_tax_carryover_api.py::_seed_clan`). Следствие: **чинить TRUNCATE
нельзя** — вскроются десятки порядко-зависимых тестов. Это отдельная задача
(не в объёме A61).

**Решение (выбрано владельцем: самый надёжный вариант).** В финал фикстуры
добавлен `db.engine.dispose()` — пул движка закрывается сразу после теста,
живым остаётся максимум один пул. Фикстура **осталась function scope**
намеренно: `test_auth.py` деактивирует `testuser`, а `test_user_role_fk.py`
меняет роль admin — оба полагаются на пересоздание сид-пользователей на
каждый тест. Вариант `scope='session'` их сломал бы (сидинг стал бы
однократным), а `NullPool` замедлил бы каждый тест.

**Важная деталь реализации.** `db.session.remove()` и `db.engine` требуют
app-контекста — вызов вне `with app.app_context()` даёт
`RuntimeError: Working outside of application context` в teardown каждого
теста (проверено: 446 passed + **278 errors**). Сессию снимает собственный
teardown flask-sqlalchemy, поэтому вручную `db.session.remove()` звать не
нужно.

**Проверка после правки:**

| | До | После |
|---|---|---|
| Прогон на хосте | 435 passed, 11 errors | **446 passed, 0 errors** |
| Соединений во время прогона | 34 → 94 → 105 (max 100) | **9, стабильно** |
| Повторный прогон | — | **446 passed** (два раза подряд) |

**Остаточный долг (не в объёме A61).** `_truncate_all()` по-прежнему молчаливый
no-op, поэтому тесты остаются **порядко-зависимыми**: каждый, кому нужна
чистота, обязан чистить свои строки сам. Список таких мест — в
`tests/test_tax_carryover_api.py::_seed_clan` и подобных.


**Почему это ловушка для разработчика.** Номера падающих тестов **меняются от
прогона к прогону** (в разных прогонах это `test_treasury_summary_api`,
`test_user_role_fk`, `test_treasury_reassign`, `test_treasury_pair_service`…):
зависит от того, сколько пулов накопилось к моменту. В изоляции каждый из них
проходит. Легко принять за регрессию от своего изменения — я на это
наступил, потратил цикл на стэш своей правки, чтобы доказать, что базовая
линия такая же.

**Как отличить «моя правка сломала» от «пул исчерпан»:** сравнить с базовой
линией через `git stash`; проверить падающий файл в изоляции (проходит);
посмотреть `SELECT count(*) FROM pg_stat_activity` во время прогона (упирается
в 100 — это пул, а не тест).

**Рекомендация.** Вариантов три, и у каждого своя цена — выбор за владельцем:

1. `scope='session'` у фикстуры `app` — один движок на сессию, соединений

2. `db.engine.dispose()` в финале фикстуры — освобождает пул после каждого

3. `poolclass=NullPool` в тестовой конфигурации — соединение на запрос, без

До решения считать **11 errors базовой линией хоста**, а не регрессией, и не
«чинить» падающие тесты — они не сломаны.

#### A52. [прочитано] Токены сессий хешируются голым SHA-256 без соли

**Severity: Low (в контексте A41/A42 — Medium).** Где:
`backend/shared/rbac/models.py:106-108`
(`hashlib.sha256(token.encode()).hexdigest()`).

Пароли хешируются bcrypt (`shared/middleware/auth.py:14`), а токены сессий —
не salted SHA-256.

**Последствие.** Токены генерируются `secrets.token_hex(32)`
(`features/auth/routes.py:37`) — то есть 256 бит энтропии, и оффлайн-подбор
непрактичен. Но утечка таблицы `session_token` даёт готовые хеши, по которым
можно проверить утечку самого токена из логов (см. A41) — а пароли при такой
утечке были бы защищены bcrypt-ом, а токены нет.

**Рекомендация.** HMAC-SHA256 с серверным секретом либо bcrypt.
